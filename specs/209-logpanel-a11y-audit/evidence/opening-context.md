## What We're Building

A reproducible WCAG 2.1 AA accessibility audit for the LogPanel — the component that shows the user what Debrief has done, when, and on whose behalf. The audit walks every LogPanel Storybook story across the three themes we support (`light`, `dark`, `vscode`), runs axe-core against each rendered state, and produces two artefacts: a machine-readable JSON dump for machines to diff, and a curated markdown report at `specs/176-log-panel-ux/evidence/a11y-audit.md` for humans to read. Findings are classified as `fix-now`, `accepted`, or `deferred`, and those classifications survive across re-runs so the report becomes a living baseline rather than a snapshot. Every serious and critical violation found during this pass is closed on the same branch before we call the feature done.

## How It Fits

Feature 176 gave the LogPanel roving tabindex and `aria-selected`, but parked the full a11y sweep until we had time to do it properly. This is that time. The runner generalises the pattern already used by `apps/spec-navigator`'s a11y suite — same `@axe-core/playwright` version, same static-build discipline — so the repo ends up with one accessibility toolchain rather than two drifting ones. The audit lives under feature 176's evidence directory because it belongs to that component's continuing story; feature 209 is just the mechanism that keeps the story truthful. More broadly, this aligns with the constitution's defence-grade reliability and documentation principles: the audit trail the LogPanel renders has to be usable by keyboard and screen-reader users, and the evidence that proves it has to outlive the engineer who first wrote it.

## Key Decisions

We drive the audit from a built static Storybook rather than the dev server so runs are deterministic and drop straight into CI later. Stories are discovered dynamically from Storybook's `index.json`, filtered by `importPath.startsWith('./src/LogPanel/')` — adding a new LogPanel story picks up coverage automatically with no runner edits. Axe is scoped to `#storybook-root` so Storybook's own chrome never pollutes findings. We audit the static render of each story only; interaction-only states become follow-ups, which is honest rather than over-reaching, and the existing story set already covers selected, disabled, empty, and flipped states. The runner exits non-zero on serious or critical findings so wiring it into `.github/workflows/ci.yml` is a one-line change once we understand its flake profile, but we are deliberately not turning that gate on yet. And we preferred two artefacts over one: JSON for diffing, markdown for reading, with a post-processor that merges the previous run's classifications so curated context is not lost between passes.
