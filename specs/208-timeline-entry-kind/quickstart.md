# Quickstart: Using the TimelineEntry `kind` discriminator

**Feature**: 208-timeline-entry-kind
**Audience**: Developers adding or reviewing LogPanel / provenance code after this feature ships.

This is a pocket guide for the three patterns you will use most. Longer rationale lives in `spec.md`; design detail in `data-model.md`.

## 1. Detecting a manual-checkpoint entry

```ts
// ✅ Correct — semantic gate
if (entry.kind === 'snapshot') {
  // render manual-checkpoint placeholder, hide duration, etc.
}

// ❌ Wrong — uses visual category as a semantic signal
if (resolveToolCategory(entry.toolName).category === 'snapshot') { ... }
```

The second form is reserved for **rendering** decisions (icon glyph, colour chip) inside `ToolCategoryIcon`. A reviewer seeing it outside that layer should flag it.

## 2. Writing an exhaustive switch over kinds

```ts
function labelForKind(k: TimelineEntryKind): string {
  switch (k) {
    case 'snapshot': return 'Manual checkpoint';
    case 'tool':     return 'Tool invocation';
    case 'tune':     return 'Tune marker';
    // No default needed — the compiler enforces exhaustiveness.
  }
}
```

If you add a new value to `TimelineEntryKind`, the compiler will flag every switch that hasn't been updated. That is the SC-004 guarantee — treat it as a feature, not an inconvenience.

## 3. Producing a TimelineEntry in a test or Storybook fixture

```ts
// VS Code host projections always set `kind`. Tests and fixtures may omit
// it — consumers treat undefined as 'tool' — but it is clearer to be
// explicit when the kind matters for the test.

const sampleSnapshot: TimelineEntry = {
  activity_id: 'fixture-1',
  timestamp: '2026-04-22T10:00:00Z',
  toolName: 'manual-checkpoint',
  tool_version: '1.0.0',
  parameters: {},
  usedFeatureIds: [],
  generatedFeatureIds: [],
  execution_duration: 'PT0S',
  generated_result_id: null,
  operationCategory: 'calculation',
  kind: 'snapshot',  // ← be explicit in snapshot-asserting tests
};
```

## 4. Emitting a LogEntry with an explicit kind (future work)

Not done by feature 208, but for authors of follow-up features:

```python
# Python (service side)
from debrief_schemas import LogEntry, ActivityType

entry = LogEntry(
    activity_id="...",
    timestamp="...",
    was_generated_by=...,
    used=[],
    generated=[],
    execution_duration="PT0.1S",
    activity_type=ActivityType.snapshot,  # ← opt-in per feature
)
```

```ts
// TypeScript (service or host side)
const entry: LogEntry = {
  activity_id: '...',
  timestamp: '...',
  was_generated_by: { ... },
  used: [],
  generated: [],
  execution_duration: 'PT0.1S',
  activity_type: 'snapshot',  // ← opt-in per feature
};
```

Existing writers that do not set `activity_type` continue to work unchanged — the field is optional and the projection falls back to `'tool'`.

## 5. What to check in a PR review

1. **Grep for semantic leaks**: `rg "category === 'snapshot'"` — any hit outside `shared/components/src/LogPanel/ToolCategoryIcon.tsx` or `LogPanel.css` is a regression.
2. **Grep for tool-name kind-matching**: `rg "toolName.*===.*'manual" apps/vscode/src/views/` — should return nothing. The projection MUST read `activity_type`, not tool names.
3. **Schema adherence tests**: `task test` runs the LinkML round-trip and structural-comparison suites. A LogEntry fixture with `activity_type: 'invalid'` must be rejected.
4. **Storybook baselines**: export-tool stories (`export-png`, `export-csv`, `export-geojson`) should no longer render the "manual checkpoint" placeholder. This is intentional (Research R2). Confirm the rebaselined screenshots show normal parameter chips.

## 6. Known non-goals (do not extend in PR)

- Do NOT extend `ToolCategory` with new values to represent semantics.
- Do NOT emit `kind: 'tune'` from any code path — it is reserved for a future standalone-tune entry type.
- Do NOT merge `FileProvEntry` (file-level provenance) into the timeline as part of this feature — that is a separate effort.
