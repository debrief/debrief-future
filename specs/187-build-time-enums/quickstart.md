# Quickstart: Build-Time Enum Extraction

**Feature**: 187-build-time-enums

This is the developer-facing usage guide for the enum-bundle extraction script. It is also the executable definition of done — the acceptance scenarios from `spec.md` map onto the steps below.

## Prerequisites

- Repository checked out and `uv` workspace bootstrapped (`uv sync --all-packages`).
- Platform registry exists at `shared/data/platform-registry.json` (delivered by item #180).
- Sample catalog exists at `preview/workspace/samples/local-store/` (regenerated by item #184).

If either input is missing, see [Troubleshooting](#troubleshooting).

## Generating the bundle

From the repository root:

```bash
uv run python scripts/extract-enum-bundle.py
```

Expected output (counts will vary with catalog contents):

```text
[extract-enum-bundle] reading registry: shared/data/platform-registry.json
[extract-enum-bundle] reading catalog : preview/workspace/samples/local-store
[extract-enum-bundle] wrote           : shared/data/enum-bundle.json
  vessel-class nodes : 24
  nationalities      : 6
  exercise names     : 12
  tags               : 18
  feature tags       : 14
```

The bundle is written to `shared/data/enum-bundle.json`. **Commit the regenerated bundle alongside any change to the registry, the catalog, or the script itself.**

## Verifying the result

Run all of the following — these are the acceptance scenarios from `spec.md` translated to commands.

### 1. The bundle is well-formed JSON with the expected sections

```bash
python -c "import json; b=json.load(open('shared/data/enum-bundle.json')); print(sorted(b.keys()))"
# → ['_meta', 'exercise_names', 'feature_tags', 'nationalities', 'tags', 'vessel_class_tree']
```

### 2. Re-running with no input changes is byte-identical

```bash
sha256sum shared/data/enum-bundle.json
uv run python scripts/extract-enum-bundle.py
sha256sum shared/data/enum-bundle.json
# → both checksums identical
```

### 3. Counts match a hand-spot-check of one item

Pick any item.json:

```bash
jq '.properties["debrief:tags"], .properties["debrief:feature_tags"], .properties["debrief:platforms"][].nationality' \
  preview/workspace/samples/local-store/core--boat1/item.json
```

Then confirm every value listed appears in the corresponding bundle section:

```bash
jq '.tags + .feature_tags + .nationalities | unique' shared/data/enum-bundle.json
```

### 4. Bundle stays small enough for an LLM prompt

```bash
wc -c shared/data/enum-bundle.json
# → expect a few thousand to a few tens of thousands of bytes
```

### 5. Schema validation (optional — for CI integration in #188)

```bash
uv run python -c "
import json, jsonschema
schema = json.load(open('specs/187-build-time-enums/contracts/enum-bundle.schema.json'))
bundle = json.load(open('shared/data/enum-bundle.json'))
jsonschema.validate(bundle, schema)
print('OK')
"
```

## Pointing the script at fixture inputs

For tests or experiments:

```bash
uv run python scripts/extract-enum-bundle.py \
  --registry path/to/test-registry.json \
  --catalog  path/to/test-catalog-dir \
  --output   /tmp/test-bundle.json
```

All three flags are optional; omitting any falls back to the canonical default.

## Running the unit tests

```bash
cd shared/data
uv run pytest tests/test_enum_bundle.py -v
```

Tests cover deduplication, deterministic ordering, missing-optional-field handling, registry-tree projection, and the exercise-name parse rule. Add new fixtures under `tests/fixtures/catalog/` when introducing new edge-case scenarios.

## When to regenerate the bundle

Re-run the script (and commit the new `enum-bundle.json`) whenever any of these change:

- `shared/data/platform-registry.json` (new vessel class, new platform, edited nationality, etc.)
- The sample catalog at `preview/workspace/samples/local-store/` (new tags, new exercises, etc.)
- The script or the bundle-builder library (`scripts/extract-enum-bundle.py`, `shared/data/src/debrief_data/enum_bundle.py`).

CI does not regenerate the bundle automatically; the committed artefact is the source of truth shown to PR reviewers.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `Registry file not found: …/platform-registry.json` (exit 1) | Working directory is not the repo root, or the registry hasn't been delivered yet (item #180). | `cd` to the repo root; verify `shared/data/platform-registry.json` exists. |
| `Catalog directory not found: …/local-store` (exit 1) | Sample catalog hasn't been regenerated yet (item #184). | Run `uv run python scripts/regenerate-sample-catalog.py` first. |
| `Invalid registry format: …` (exit 2) | Registry JSON is malformed or violates the schema. | Read the error message — it names the offending key/path. Fix the registry, re-run. |
| Bundle is unexpectedly larger than expected | Catalog has grown a lot, or non-canonical duplicates have crept in. | Inspect the bundle's `tags`/`feature_tags` lists for casing variants; if found, normalise the source data. |
| Two reruns produce different bundles | The script picked up a transient input change (e.g. a half-imported catalog item). | Ensure no other process is writing to the catalog; re-run. If the difference persists, file a bug — determinism is required (FR-008). |
