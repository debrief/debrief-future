# Contract — Service worker behaviour

The Backlog Navigator's service worker is generated by `vite-plugin-pwa`
in `generateSW` mode (Workbox-backed). This document is the **behavioural
contract**: cache zones, lifecycle, update protocol, offline behaviour.

## File layout

| Path | Source | Purpose |
|------|--------|---------|
| `dist/sw.js` | Generated by Workbox at build | The active service worker |
| `dist/workbox-*.js` | Generated by Workbox at build | Workbox runtime |
| `dist/registerSW.js` | Generated by `vite-plugin-pwa` | Auto-registration helper (we **don't** use this — we register from React; see below) |
| `src/pwa/registerSW.ts` | Hand-written | The React-side registration that consumes `virtual:pwa-register` |
| `dist/manifest.webmanifest` | See `pwa-manifest.md` | n/a (linked by SW for installability) |

## Registration

`registerSW.ts`:

```ts
import { registerSW } from 'virtual:pwa-register';

export type ServiceWorkerUpdateState =
  | { kind: 'up-to-date' }
  | { kind: 'update-available'; reload: () => Promise<void> }
  | { kind: 'updating' };

export function startServiceWorker(
  onUpdate: (state: ServiceWorkerUpdateState) => void,
): void {
  const update = registerSW({
    immediate: true,
    onNeedRefresh() {
      onUpdate({
        kind: 'update-available',
        async reload() {
          onUpdate({ kind: 'updating' });
          await update(true);
        },
      });
    },
    onOfflineReady() {
      // First install complete; the app shell is now cached.
      // Surface no UI affordance — the user already sees the app.
    },
    onRegisterError(err) {
      console.error('[pwa] service worker registration failed', err);
      // Non-fatal — the app still works without a SW.
    },
  });
}
```

`main.tsx` calls `startServiceWorker(setUpdateState)` at boot. Failures are
logged (per Article I.3 — no silent failures) but do not block the React
mount.

## Cache zones

Two zones, both configured in `vite.config.ts`'s `VitePWA` plugin block.

### Zone A — App shell (precache)

**Strategy**: `precache + cacheFirst`

**Precache manifest**: every file emitted by Vite into `dist/` whose
extension is one of: `.html`, `.js`, `.css`, `.woff2`, `.png`, `.svg`,
`.ico`, `.webmanifest`. The manifest is hashed by Workbox at build time;
each file's content-hash is the cache key, so a redeployed build with one
changed JS file invalidates only that file.

**Cache name**: Workbox-generated, prefixed `workbox-precache-v2-`.

**Behaviour at request time**:
1. Service worker intercepts `fetch` for any precached URL.
2. Returns the cached response immediately (`cacheFirst`).
3. Out-of-band, Workbox compares cache integrity hashes; if drift, the SW
   marks itself "waiting" and fires the update lifecycle (next section).

### Zone B — GitHub data fetch (no cache)

**Strategy**: `networkOnly`

**Routes**:
- `https://api.github.com/repos/debrief/debrief-future/contents/BACKLOG.md*`
- `https://api.github.com/repos/debrief/debrief-future/contents/BACKLOG.md` (all methods including PUT)
- `https://raw.githubusercontent.com/debrief/debrief-future/*/BACKLOG.md`

**Behaviour**:
- Online: SW is a transparent passthrough.
- Offline: SW lets the fetch fail; the app's existing error handler
  catches the `TypeError` (network error) and renders the offline empty
  state per FR-019.

**Why no cache**: spec FR-019 forbids displaying stale data without
clearly indicating it; caching `BACKLOG.md` would create exactly that risk
(see research R-2). The `networkOnly` strategy ensures the offline state
is detectable and the user is never misled.

## Lifecycle

### Install

1. Fresh user visits the navigator (no SW yet).
2. Workbox SW installs in the background.
3. On install complete, `onOfflineReady` fires (we don't surface a banner
   — the app is already visible and working).
4. Subsequent navigations are SW-backed.

### Update detection

1. User visits the navigator after a redeploy.
2. Browser fetches `/sw.js`; Workbox detects the new precache hash.
3. New SW installs in the background, enters `waiting` state.
4. `onNeedRefresh` fires.
5. `<UpdatePrompt>` banner mounts: "An updated Backlog Navigator is
   ready. Reload?"
6. User confirms → `update(true)` is called → `skipWaiting` activates the
   new SW → page reloads → user sees the new version.

**Window between detection and reload**: the *old* SW remains active;
data fetches still work. Dirty edits are preserved across the reload by
the existing #242 dirty-edit `localStorage` snapshot (we MUST verify this
in implementation testing — Edge Case "service worker update").

### Storage eviction

If the OS evicts the SW cache (low-storage condition), the next online
navigation re-fetches everything from network. Workbox handles this
transparently. No user-visible change beyond a one-time slower load.

## Update prompt UI contract

Component: `<UpdatePrompt>` in `src/pwa/UpdatePrompt.tsx`.

| State | UI |
|-------|----|
| `up-to-date` | Component renders nothing (`return null`). |
| `update-available` | Banner at the top of viewport (above sticky push bar): "An updated Backlog Navigator is ready." + two buttons: "Reload" (primary) and "Dismiss" (secondary). |
| `updating` | Banner switches to spinner + text "Updating…". Disappears when the page reloads. |

**Dismiss behaviour**: closes the banner for the current session only. The
SW remains in `waiting` state; on the next page navigation, the
`onNeedRefresh` re-fires and the banner returns. (No "remind me later"
persistence — Article XII community engagement value of "responsive
engagement" applies; users should be able to update easily.)

**Time-to-surface SLO**: ≤ 60 seconds from launch (SC-011). With
`immediate: true` registration, the new SW typically activates within
~2 seconds of page load.

## Forbidden behaviours

These would violate spec invariants and MUST NOT be added:

1. **Auto-update without prompt** (`registerType: 'autoUpdate'`) — would
   silently reload mid-session and lose dirty edits. Forbidden by FR-020.
2. **Caching GitHub responses** — would risk stale-data display.
   Forbidden by FR-019 / R-2.
3. **Custom SW logic that mutates IndexedDB** — out of scope per
   Assumption A-1; reopens the offline-edit conflict-resolution surface.
4. **Background sync** (`workbox-background-sync`) — out of scope per
   spec; would imply queued offline edits.
5. **Push notifications** (`Push API`) — out of scope per spec.

## Failure modes

| Failure | SW behaviour | UX |
|---------|--------------|-----|
| SW registration fails (e.g. unsupported browser) | `onRegisterError` fires; console error | App still works (no offline shell, no install) — degrades gracefully |
| Precache fails (network drop mid-install) | SW remains "installing"; old SW stays active | Next visit retries |
| `update(true)` reload fails | Page does not reload; banner returns to `update-available` | User can retry by tapping Reload again |
| GitHub fetch fails offline | `networkOnly` lets the fetch reject; app catches the error | Offline empty state per FR-019 |

## Test contract

The following must be verified in implementation:

1. **Unit**: `registerSW.ts` correctly maps Workbox lifecycle events to
   `ServiceWorkerUpdateState` transitions.
2. **E2E (Playwright)**: An `update-available` state is rendered when the
   SW reports a waiting version. (Mocked via Playwright's
   `page.addInitScript`.)
3. **E2E (Playwright)**: Offline mode (Playwright's `context.setOffline(true)`)
   with cached app shell renders the offline empty state, **not** a white
   screen or crash.
4. **Lighthouse CI**: PWA audit's "Service worker controls page and
   start_url" passes; "Web app manifest meets the install criteria"
   passes; overall PWA score ≥ 90.
