## What We're Building

The sample catalog is the demo data foundation for Future Debrief -- 63 items covering maritime exercises, each with tracks, sensor data, and annotations. It works. But it carries metadata in the wrong shape.

Right now, each catalog item stores nationality, vessel class, and track name as three separate flat arrays. German frigate BAYERN and British submarine AMBUSH both contribute to a shared `debrief:nationalities` list and a shared `debrief:vessel_classes` list, with no way to tell which nationality goes with which vessel. Ask "show me plots with a German frigate" and the system has to guess. It might match a plot that has a German vessel and a frigate, but not the same platform.

The new `debrief:platforms` format bundles identity, nationality, vessel class, and domain into per-platform records. We built this format in #181 (schema updates) and #182 (import pipeline validation). Now we need the sample data to actually use it.

The plan is blunt: delete the existing catalog, reimport the same source files through the current pipeline, then enrich with exercise metadata. A clean import naturally produces the new format -- no migration code, no field-by-field patching, no mixed-state artifacts.

## How It Fits

This is step 5 of 11 in the E10 epic (NL-Assisted Catalog Discovery). The preceding features laid the groundwork:

- #180 built the platform registry (10 known vessels with nationality, class, domain)
- #181 updated the LinkML schema to carry `debrief:platforms` arrays
- #182 wired the import pipeline to warn on unregistered platforms
- #183 documented the architectural decisions

This feature produces the clean data that everything downstream depends on. Features #185 through #190 -- CQL2 array filtering, filter bar chips, enum extraction, natural language search -- all assume structured platform records exist in the catalog. Without this regeneration, those features would work against stale data and give misleading results.

## Key Decisions

- **Three-phase pipeline, one script**: Extract source files from the existing catalog into a staging directory, delete the catalog, reimport via `import_legacy_data()`, then enrich with `enrich-legacy-catalog.py`. One orchestration script runs the whole sequence. The import pipeline and enrichment script are unchanged -- we're just re-running them on clean inputs.
- **Source file preservation via staging**: The original `.rep`, `.dpf`, and `.dsf` files live inside the catalog being deleted (as STAC assets). We copy them to a temp directory before deletion, then reimport from there. Can't import from a directory you're about to nuke.
- **No changes to existing pipeline code**: The import pipeline already creates items without deprecated flat fields. The enrichment script already writes only `debrief:platforms`, `debrief:tags`, and `debrief:feature_tags`. A fresh run produces clean output by construction, not by migration logic.
- **Thumbnails are out of scope**: The current catalog has thumbnail images, but these were generated by a separate browser automation process (#174). Reimport won't produce them. Items will be structurally complete but visually bare until thumbnails are regenerated independently.
- **Deterministic output**: The enrichment script uses `random.Random(42)` for all randomized assignments -- exercise names, tag selection, platform allocation to exercises. Same seed, same output. Run it twice, get identical results.
- **No test dependencies on catalog content**: We checked -- no unit tests read from the sample catalog. Tests use independently constructed fixtures. So regenerating the catalog won't break anything.
